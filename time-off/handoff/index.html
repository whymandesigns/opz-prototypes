Time off: developer handoff

Everything needed to build self-service time off into the member profile's Time Off tab: requesting, upcoming time off, the calendar, history, and a manager's approvals. The components shown are the real ones from the prototype, not drawings.

Clickable prototype: open the Time off prototype. It opens on your own profile as an employee. The dark bar at the bottom ("Prototype only · View as manager") switches to someone who has direct reports.

Context

Today an employee requests time off, and a manager approves it, only in the Time Off Slack app (TOFF-SLACK-001, TOFF-SLACK-002, TOFF-LIFE-002). The web app has two read-mostly places: the reporting pages at /time-off for managers and time-off administrators (TOFF-REP-001), and a view-only Time Off tab on every member profile (TOFF-PROF-001 to -004). Administrators can add and edit anyone's time off from the reporting pages, auto-approved (TOFF-WEB-001, TOFF-WEB-002).

This feature brings the Slack app's employee and manager flows into the web app, inside the existing profile tab, so nobody needs Slack to request, follow or approve time off. The rules of the flow do not change: the same statuses, the same approver, the same validation. Rule IDs throughout refer to the test oracle in topteam/test-oracle/.

Where it lives

On the member profile, /people/:userId/time-off, the last tab of the profile's own tab strip (PROF-TABS-001). There is no new page and no new sidenav item; People stays the active section.

Who is covering

Clicking the picker on a card opens a menu in place. It is a multi-select: a time off can have several covers, and each can be a co-worker, a Slack channel or a Slack user group (TOFF-SLACK-009). Accessibility

  • Icon-only buttons carry a label: "Edit time off", "Previous month", "Next request".
  • The hours choice is a radiogroup labelled with its day, "First day, hours".
  • The coverage menu is a labelled dialog; focus moves to its search field on open and Escape closes it.
  • Modals trap nothing new: they use the kit modal, closed by Escape, the close button or a click on the overlay.
  • Status is never colour alone: every tag has its word, and the calendar legend names both fills.
  • The calendar is a real table with column headers per weekday.

Data model

The prototype holds this shape in a JavaScript array. It mirrors what the product already stores for an OOO event; the names are a suggestion, not the existing contract. Where an operation exists today behind the Slack app or the admin modal, reuse it so that a request made or answered in either place resolves in both.

TimeOff {
  id: string
  member: { id, name }
  type: { id, name, group: "Short-Term Leave" | "Extended Leave" | "Other" }
  reason: string | null                 // "What is this OOO for?", max 150
  firstDay: date, lastDay: date         // in the member's time zone
  firstDayHalf: { leavingAt: time } | null
  lastDayHalf:  { returningAt: time } | null
  recordedDays: number                  // weekday 1, half day 0.5, weekend 0
  status: "pending_approval" | "approved" | "denied" | "cancelled"
  approvalStage: "manager_pending" | "executive_pending" | "completed"
  awaiting: { id, name } | null         // who the request is waiting for
  replaces: { id, firstDay, lastDay, recordedDays } | null   // set on a change request
  covers: [{ kind: "person" | "channel" | "user_group", id, name, role?: string }]
  statusUpdates: [{ status, by, at, previousStatus }]
  operations: { edit: boolean, cancel: boolean, assignCover: boolean }
}

ApprovalRequest = TimeOff + {
  requestedAt: datetime
  recordedThisYear: number              // excluding this request
  overlapping: [{ member, firstDay, lastDay, status }]
  needsExecutive: { id, name } | null
}

Own profile
  upcoming time off        pending or approved, lastDay >= today
  history(from, to)        the rest overlapping the period, plus the period total
  request / edit / cancel  as the member, through the approval flow
  add / remove cover       saved immediately

Approver
  my team's upcoming       direct reports, approved (or awaiting the executive), lastDay >= today
  requests waiting for me  at my stage, with the context above
  approve / deny(note?)    the same mutations the Slack buttons run today

The web mutations that exist today (createTimeOffEvent and its edit and cancel counterparts) require "Manage org-wide time off" and approve immediately (TOFF-PERM-012, TOFF-WEB-002). Self-service needs the Slack app's behaviour instead: acting as the member, starting at Pending approval.

Prototype only

  • The dark bar at the bottom ("Prototype only · View as manager") is not part of the product. In the product the manager section appears for anyone who has direct reports.
  • The person and all data are made up. "Today" is fixed at November 20, 2026 so the screen reads the same on any day. Nothing is saved; a reload restores the sample data.
  • Only the Time Off tab is built. The other profile tabs, Edit profile and the more menu do nothing. The map is a grey placeholder.
  • The anniversary badge is the product's own image (back-end/public/images/badges/small/milestone/7.png), embedded.
  • The round button bottom right is the reviewers' comment tool.

Open questions

  • What "Total Time Off" counts. Shipped: everything recorded in the range, upcoming included. Here: only what already happened, with upcoming shown separately. Pick one, or show both.
  • Role title for a cover. Required by the product today (TOFF-VAL-009), left out here. Either relax the rule for covers added from the web, default the title, or add a field to the picker.
  • Reaching the approver without notifications. The tab count is visible only on the manager's own profile. If in-app notifications do not ship, consider a count on the avatar menu item, and keep the Slack approval message.
  • A way in to the reporting pages (/time-off Summary and Events), once the avatar menu item points at the profile tab.
  • Team view scope. "My team" lists direct reports only. Whether it should include indirect reports, as the reporting pages can, is not decided.
  • Approving from a report's profile. Should the manager also see Approve and Deny on the Time Off tab of the person who asked? Not designed.
  • The executive's queue. The second sign-off needs the same section for the executive; confirm it lives on their own profile too.
  • Denial note. The oracle has no rule for a reason on denial. The optional note in the deny dialog is new.
  • Pending days on the calendar (TOFF-Q-007), and whether other viewers should ever see them.
  • Status history. Recorded by the product (TOFF-LIFE-007) but not shown in this design. Decide whether the member should be able to see it.
  • Administrators. "Add time off" for another member stays on the reporting pages; whether it should also be reachable from that member's profile is not designed.
  • Tenant scope. Requests and approvals run only on the TopTeam tenant today (TOFF-PERM-003). Confirm the web flow is meant for Operationalize tenants without the Slack app, and what replaces the Slack status and channel announcements there.
  • Design system. The calendar is page-scoped CSS, and the time-off grey is lighter than the product's. Both belong in designmd.
