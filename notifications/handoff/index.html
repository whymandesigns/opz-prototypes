Notifications: developer handoff

Everything needed to build in-app notifications for Operationalize: the bell, the panel, the full page, every row state, the rules behind them and the 66 notification types. The components shown are the real ones from the prototype, not drawings.

Clickable prototype: open the Notifications prototype. It opens with the bell panel showing; switch to "Notification types" on the page for the catalogue.

Context

The product has no in-app notifications today. Its notification framework delivers through Slack only; e-mail and in-app are reserved channel values with no adapter (PLAT-NOTIF-011). People have no notification preferences (PLAT-NOTIF-012), and someone without a linked Slack account receives nothing (PLAT-NOTIF-003).

This feature adds an in-app channel for the events the app already announces, plus seven events it does not announce yet. Rule IDs throughout refer to the test oracle in topteam/test-oracle/.

The prototype at 1280 px: panel open from the bell, full Notifications page behind it. Source: opz-prototypes/notifications/prototype/index.html, branch notifications.

Panel states

Notification row

One component, article.notification, used unchanged in the panel and on the page.

  1. Lead, 32 px. An avatar (.avatar.avatar-md, initials or photo) when a person caused the event; otherwise the area icon in a round .notification-icon.
  2. Text, 14/22 regular. People and object names are semibold. One or two sentences, no trailing call to action.
  3. Meta, 12/18 muted: area name, a middle dot, then the time.
  4. Actions, optional. .btn.btn-secondary.btn-xs, 8 px apart, 8 px under the meta line. Decisions first, the shortcut link last.
  5. Read toggle, a 24 px hit area holding an 8 px dot in --color-accent when unread.

After a decision

Answering replaces the buttons with one status tag, marks the row read, removes it from Needs action and shows a success toast. The row stays in the list.

Notification settings

A modal opened from the settings icon in the panel or the button on the page. This is new behaviour: there are no per-person preferences today (PLAT-NOTIF-012). One row per area, one switch per channel. Decisions always appear in the app whatever the switches say.

Accessibility

  • Bell: aria-haspopup="true", aria-expanded kept in sync, label carries the unread count.
  • Tabs: role="tablist" and role="tab" with aria-selected. Count badges are read as part of the tab name.
  • Rows are article elements. The lead avatar or icon is aria-hidden; the text already names the person and the area.
  • Read toggle: a real button with aria-label "Mark as read" or "Mark as unread", and the same text as a tooltip on the left.
  • Esc closes the panel and returns focus to the bell. Focus rings use --color-border-focus, 2 px, 2 px offset.
  • Toasts sit in one aria-live="polite" region. Unread state is never colour alone: the toggle's label changes too.

Data model (proposal)

The prototype holds this shape in a JavaScript array. Field names are a suggestion for the API, not an existing contract.

Notification {
  id: string
  type: string            // one of the 66 type keys, e.g. "time_off.requested"
  area: "rob" | "work" | "okr" | "feedback" | "recog" | "timeoff" | "account"
  kind: "decide" | "do" | "fyi"
  actor: { id, name, initials, avatarUrl } | null   // null: show the area icon
  tone: "default" | "warning" | "danger"            // icon chip colour only
  body: RichText          // sentence with bold spans for people and objects
  target: { url: string, label?: string }           // row click; label = shortcut button
  actions: [{ key, label }]                         // decisions only, in display order
  resolution: { key, label, outcome: "positive" | "negative", by, at } | null
  createdAt: datetime
  readAt: datetime | null
}

GET  /notifications?view=all|action|unread&area=&limit=&cursor=
GET  /notifications/counts          -> { unread, needsAction }
POST /notifications/:id/read        POST /notifications/:id/unread
POST /notifications/read-all
POST /notifications/:id/actions/:key   // runs the same mutation the Slack button runs today

Decision buttons should call the existing mutations behind today's Slack buttons, so a request answered in either place resolves in both.

Open questions

  • Recipients of the seven new types are a design proposal, for example "accountable owner and earlier commenters" for a comment. They need a product decision.
  • OKR comments: the oracle confirms they exist but has no rule about notifying anyone.
  • Slack and in-app together: should an event send both by default, and does answering in one silence the other?
  • Wording of "RoB": the web app says RoB; server messages on Operationalize tenants say "Cadenced Meeting" (ROB-NOTIF-004). The prototype uses RoB.
  • Tenant scope: Recognition is off by default outside Toptal's own tenant, and time off approvals run only there today. Hide those areas, in the filter and in settings, where the feature is off.
  • Digests: several Slack messages today are batched lists (assessments, corrupted RoBs, RACI additions). In the app each item is shown as its own row; confirm that is wanted.
  • Retention and delivery: how long notifications are kept, and whether counts update live or on page load, are not designed.
  • Not included: Slack channel posts such as "meeting about to start", sign-up and password e-mails, and internal ops alerts, since none is addressed to a signed-in person.
